================================================================================
THE BIGGER FEATURES - how they actually work
================================================================================

QR CHECK-IN
-----------
Each teacher has a fixed QR code printed and kept on their desk. A student who
is signed in scans it when the class starts and again when it ends. The teacher
turns those scans into lectures.

The code
  12 characters from ABCDEFGHJKMNPQRSTUVWXYZ23456789 - no 0/O and no 1/I/L, so a
  code read off a printed card cannot be misread. Stored in teachers.qr_code,
  UNIQUE, created lazily the first time it is asked for and never changed
  afterwards (the card is printed and stuck to a desk).

  The image holds a link, origin + /scan?c=CODE, so a phone camera can open it
  too. /scan parks the code and sends the student through the login they already
  have. The code is also printed in plain text under the QR, and typing it works
  the same way.

  The code identifies the teacher and nothing else. It is not a password and
  carries no rights: scanning records attendance for whoever is already signed
  in, so the QR gives the teacher and the login gives the student.

The scan (POST /api/checkin)
  Finds the student's open row with that teacher today (out_at IS NULL).
    none               -> insert a row: session_date CURDATE(), in_at NOW(),
                          plus the scan's ip, gps and device
    under 2 minutes    -> the same tap twice; nothing changes
    2 minutes or more  -> set out_at = NOW() and
                          hours = ROUND(TIMESTAMPDIFF(MINUTE,in_at,NOW())/60,2)

  Every time comes from MySQL, never the phone, so a device set to the wrong
  country records the same moment as everyone else.

The inbox (GET /api/checkin/inbox)
  One row per student, never a batch, grouped by day. The teacher fills subject,
  topic, subtopic, remark, venue and meeting link and confirms. Confirming calls
  insertLecture and writes a lecture for that ONE student, charging their own
  time in to time out - 4:15 to 5:20 is 1.08 hours for them whatever the rest of
  the room did. Until confirmed, nothing has touched anybody's hours.

  POST /checkin/apply      the same fields across several rows of a day
  POST /checkin/confirm    several at once
  POST /checkin/manual     a student who came without a phone; the row is not
                           stamped as scanned, and the inbox shows "added by
                           hand" so real scans stay distinguishable
  DELETE /checkin/:id      marks it Discarded; never erased

  Guards: a teacher only ever sees and touches their own rows; an admin can work
  any of them; a row with no time out cannot be confirmed; a row cannot be
  confirmed twice; anything over 3 hours is flagged in red and asks for a
  confirmation, because it is almost always a forgotten scan out.

Client files: pages/student/CheckIn.tsx, pages/Scan.tsx,
components/AttendanceInbox.tsx, pages/admin/Attendance.tsx,
pages/faculty/Attendance.tsx, components/QrCode.tsx, lib/qr.ts.


LECTURE ENTRY
-------------
components/LectureSheet.tsx, shared by the teacher's page and the admin's page
for a teacher (teacherId is what tells them apart).

A sheet, not a dialog: fill the line across the top, press Save, and the class
drops into the list below under the same headings - the institute kept this in
Excel and the staff already know that shape. Nine fields across two lines so no
box is too narrow, stacked below lg. Hours are never typed; they follow from the
start and end time.

Editing a logged class also adds and removes students on it, without deleting
and re-entering the class.


FEE IMPORT DRAFTS
-----------------
pages/admin/Finance.tsx. Imported bank rows that could not be matched wait as
cards: the bank's own facts on top, the fields to fill underneath, Assign and
Discard at the bottom right, and a flag saying new / already recorded / already
in drafts. This is the pattern the attendance inbox copies.


SPEECH TO TEXT
--------------
AssemblyAI, for dictating the lecture remark. Built and working, then HIDDEN at
the client's request: components/DictateButton.tsx exports SPEECH_ENABLED =
false and returns null.

If it is ever switched back on, the fix for losing the first words must go back
in: start listening (getUserMedia) immediately and buffer, rather than waiting
for the token and the socket. That fix is NOT currently in the file - it was
lost in a revert.


FORGOTTEN PASSWORD
A code to the email on file, then a password the system makes up.

The thing that shapes all of it: users.email is the LOGIN NAME, not an address.
Most are "sachin.chawan" or "myra". The real address, where there is one, sits
on students.email / parents.email / teachers.email, which is what
utils/passwordReset.ts contactEmailFor() looks through, in that order.

So the screen asks for the USERNAME. It cannot ask for the email: thirty
addresses on file belong to more than one account (two children and their
father on one Gmail), so an address does not say whose password to reset.

Only about 131 of 303 active logins have an address anywhere today - the admin
and the super admin have none at all, so put one on those two rows before this
goes live. Nothing has to change as the office fills the rest in: the address is
looked up at the moment someone asks.

  POST /api/auth/forgot        username -> a six-digit code is emailed
  POST /api/auth/forgot/reset  username + code -> the new password, once

  The code       bcrypt-hashed, never stored in the clear. Ten minutes, one use.
                 Five wrong tries burns it. Three per account per quarter hour,
                 twelve per connection per hour.
  Same answer    whether the login exists or not - a different reply is a way to
                 find out which logins are real. The one exception is an account
                 with NO email, which is told to ring the office: it does confirm
                 the login exists, and it is still better than leaving a family
                 waiting for a code that was never coming.
  The password   shown once on screen, never emailed - an old mailbox must not be
                 a permanent key. Syllables and digits ("dafora499") because it
                 is read off a screen and typed on a phone.
  Afterwards     users.must_change_password is set, and App.tsx then shows
                 nothing but ChangePasswordRequired until they pick their own.

Signing out the other devices. A password change raises users.token_version
(utils/tokenVersion.ts); every token carries the number it was signed with and
requireAuth refuses anything lower. Checked on every request, so it is cached
for 30 seconds - a reset takes up to half a minute to reach another running
instance. The reply to /auth/change-password carries a fresh token, stored by an
interceptor in api/client.ts so the device that did the changing stays in.

Client files: pages/ForgotPassword.tsx, pages/ChangePasswordRequired.tsx.


WEB PUSH NOTIFICATIONS
The notification that arrives with the app closed. utils/push.ts notify() is the
whole interface - one call, never throws, writes to notification_log.

  New registration       -> admin + super admin   (routes/auth.ts)
  Registration approved  -> the student + parents (routes/registrations.ts)
  Hours statement sent   -> the parents           (routes/email.ts)
  Checked in             -> the teacher + parents (routes/checkin.ts)
  Checked out            -> the parents           (routes/checkin.ts)

The student is NOT notified of their own check-in: they are holding the phone
that just scanned and the screen has already told them.

NOTHING WITH A FIGURE IN IT. A notification is read off a lock screen by whoever
has the phone, and can land on a device whose sign-in expired weeks ago. "Your
hours statement has been updated", and a tap opens the app.

Opt-in, PER DEVICE. A laptop says nothing about a phone - the card says so,
because it is the second thing everyone asks. Expect well under half of parents
to turn it on, so nothing may depend on a push having arrived.

iPhones only get notifications once the site is ADDED TO THE HOME SCREEN -
Safari has no PushManager in an ordinary tab, and the failure is otherwise
invisible. lib/push.ts detects that case by name and the card explains the
Share menu rather than saying "unsupported".

  GET  /api/push/key        the VAPID public key + whether push is set up
  POST /api/push/subscribe  this browser; "silent" skips the confirming buzz
  POST /api/push/unsubscribe
  GET  /api/push/mine       this person's own devices

Keys: VAPID_PUBLIC_KEY / VAPID_PRIVATE_KEY in server/.env, generated once.
Replacing them silently kills every subscription anyone has already allowed.

A push service answering 404/410 means that browser is gone (cleared, or
notifications turned off in the browser itself); the row is marked is_deleted
rather than retried for ever.

Client files: public/sw.js, public/manifest.json, lib/push.ts,
components/NotificationsCard.tsx (on Settings and the parent's Profile).


THE NOTIFICATION BELL
The same notices, read inside the app. routes/notifications.ts reads
notification_log - the table utils/push.ts already writes one row of per person
per notice - so there is no second system and no second decision about who
hears what.

That is the point of it. A push only reaches someone who turned notifications
on, on that device, and most will not; a row written as 'no_device' used to be
the end of the story. It now shows in the bell the next time they open the app,
so the news reaches everybody and the push is only what makes it arrive sooner.

Every role has one - office, super admin, teacher, student, parent.

  GET  /api/notifications/count   the unread number (polled every 60s)
  GET  /api/notifications         the last 25, newest first
  POST /api/notifications/read    {} for all, or { id }
  POST /api/notifications/clear   {} for all, or { id }

Opening the bell marks what is showing as read, which clears the number; the
notices stay, tinted, until the person presses Clear all. Clearing sets
dismissed_at - hidden, never deleted, so "was this parent told?" still answers
months later.

'test' (the buzz that confirms a device works) is excluded from the feed - it is
not news, and would otherwise be the first thing in everyone's bell.

There is no top bar on desktop, so the bell sits with the theme and sign-out
buttons in the sidebar footer, and beside the theme toggle on the mobile header.

Client files: components/NotificationBell.tsx, wired in components/Layout.tsx.

THE "TURN ON NOTIFICATIONS" STRIP
components/NotificationPrompt.tsx, under the heading on the faculty, admin and
parent dashboards. It appears by itself after signing in; the browser's own
permission box only follows a press.

It is the FALLBACK. On Chrome, Edge and the other Chromium browsers the
permission box now appears by itself a second after signing in - autoAskPush()
in lib/push.ts, called from AuthContext - exactly as the location box already
does on this app. The strip is for everywhere that does not work.

Why both. Firefox and Safari IGNORE a permission request that nobody pressed
for: no box, no error, nothing. So an automatic ask alone would reach no one on
an iPhone. And the box is ONE SHOT - a person who taps Block can never be asked
again, only they can undo it - so it is asked automatically ONCE per account,
ever (localStorage pushAutoAsked:<userId>), because Chrome counts repeated
dismissals as a block. After that one attempt only the strip asks, and that
moves only when pressed.

Shown only when push is available and off. On an iPhone in a Safari tab it
shows the Add to Home Screen instruction instead, with no button - pressing one
could not work there.

"Not now" is remembered for 7 days, keyed by user id so dismissing it on a
shared office PC does not hide it for the next person. A refusal at the browser
box snoozes it too - that is not a question to repeat tomorrow.

Students have no strip: the only notice they receive is their registration
being approved, and they are not notified of their own check-in (they are
holding the phone that scanned). The switch is on their Profile if they want it.

Registering a device fires PUSH_ON_EVENT on the window. The strip and the
Settings card both listen: the automatic ask lands a second after the dashboard
has drawn, by which time the strip has already decided to show itself, and
without this it would sit there inviting someone to switch on what they just
switched on.

TO SEE THE AUTOMATIC BOX AGAIN once it has been answered, both of these have to
go - the browser remembers the permission and we remember having asked:
  chrome://settings/content/notifications  -> remove the site
  localStorage.removeItem('pushAutoAsked:<your user id>')
