================================================================================
DATABASE
================================================================================

MySQL 8. Live database name: classroom_app (schema.sql still says tuition_erp -
check which one your .env points at before running anything).


TABLES
------
  branches                  the institute's locations
  users                     every login. role ENUM('student','parent','faculty',
                            'admin','superadmin'). password_hash is bcrypt.
  students                  the student record. form_no is the institute's own
                            number and is what staff recognise, not the id.
  parents                   parent records, linked to students
  teachers                  teacher records, linked to a user; holds qr_code
  subjects                  the subject list
  student_teacher_mapping   which teacher teaches which student (and subject)

  lecture_sessions          one row per class taught
  lecture_attendees         one row per student on a class - THIS is where
                            hours are charged. UNIQUE (lecture_id, student_id).
  lecture_checkins          one row per QR scan (see 08-features.txt)

  fee_packages              hours bought, linked to the payment that bought them
  fee_transactions          money received
  ledger_adjustments        per-student overrides (pending fees, amount credited)
  hours_adjustments         manual + / - hours, each its own dated entry
  fee_import_drafts         imported bank rows waiting to be matched to a student

  app_settings              key/value institute switches (student lock,
                            permissions). Has updated_by and updated_at.
  audit_logs                every change, with ip / gps / device
  email_log                 what was sent, or why it was not


RELATIONSHIPS THAT MATTER
-------------------------
  users 1 --- 1 students        students.user_id (a student may have no login)
  users 1 --- 1 teachers        teachers.user_id
  students 1 --- n lecture_attendees n --- 1 lecture_sessions
  students 1 --- n fee_transactions 1 --- n fee_packages
  teachers 1 --- n lecture_sessions
  students n --- n teachers     through student_teacher_mapping

A lecture belongs to one teacher and carries many students. Each attendee row
carries its OWN hours_consumed - they are not required to be equal. The QR
check-in feature depends on that: each student is charged the time they
personally sat.


CONVENTIONS IN THE SCHEMA
-------------------------
  is_deleted TINYINT(1)     on nearly every table. Nothing is ever DELETEd by
                            the application - see 06-conventions.txt.
  is_active                 a separate idea from is_deleted. A student can be
                            Inactive (left the institute) without being deleted.
  created_at / updated_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP. Generated by
                            MySQL on a connection set to +04:00, so they are
                            Dubai time.
  DECIMAL for money and hours, never FLOAT.

Two different "active" flags exist and they are not the same thing:
  students.status / students.is_active  - the enrolment
  users.is_active                       - whether the login works
When switching a student off, ALL THREE are set together. Setting only the login
leaves a record that looks Active but cannot sign in, which has caused real
confusion before. The app does this correctly in
server/src/routes/students.ts (the status and archive endpoints) - copy that.


MIGRATIONS
----------
database/migrations/, named YYYY-MM-DD_what-it-does.sql. Run once each, in
filename order. They are plain SQL, applied by hand or with
  node server/scripts/run-sql.js <file>

There is no migration table and no rollback. Each file starts with
USE classroom_app; and a comment explaining WHY the change was needed. Follow
that pattern - the comments are the only record of the reasoning.


BACKUPS
-------
server/scripts/backup-db.js writes a JSON snapshot. Any script that changes
existing data writes its own backup JSON beside it first - there are many
examples in server/scripts/ (backup_merge_170_into_8.json and so on). Do the
same for anything you write.
